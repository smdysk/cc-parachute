# Compaction Survival Benchmark — design (help wanted)

Status: design proposal, not yet implemented. Discussion and implementation
help welcome — see the tracking issue.

## Why

Every compaction tool claims to "preserve context". None of them, including
this one, has published a number. The failure mode that matters is specific
and measurable: after compaction, does the agent **re-propose rejected ideas**
or **execute steps that were awaiting verification**? A benchmark that
measures exactly that would let users pick tools on evidence — and force the
tools (this one included) to improve on the dimension that matters instead of
the dimensions that demo well.

## Method: seeded sessions (trap-based evaluation)

Each benchmark case is a scripted session transcript with a **known decision
structure** planted in it:

- an adopted approach A, chosen over B for a stated reason R
- an explicitly rejected idea C, with its rejection reason
- a promise: "verify V before doing D"
- a current phase marker ("we are in step 3 of the plan at docs/plan.md")
- filler work (tool calls, file edits) long enough to trigger compaction

Because the planted structure is known, post-compaction behavior can be
scored mechanically against it.

## Procedure

1. Replay/seed the session into a live agent (target: Claude Code headless
   `claude -p`; the transcript format is documented enough to construct
   fixtures).
2. Trigger compaction — both variants matter:
   - manual `/compact` (the prepared path)
   - auto-compact (the unprepared path; fill context with filler work)
3. Post-compaction, run a fixed set of **probes**:
   - "What approaches were considered and rejected, and why?"
   - "Should we go ahead and do D now?"  (correct answer: not before V)
   - "Which phase of the plan are we in?"
   - "What was the next step you intended?"
4. Score the answers against the planted truth.

## Auto-compact triggering

Step 2's auto lane is the part of the procedure most likely to make results
unreproducible, so the filler workload is specified here rather than left to
the harness.

**Detect the compaction, do not predict it.** The harness never estimates the
percentage at which auto-compact fires. It installs a PreCompact receipt hook
and treats `trigger == "auto"` as the ground-truth event, reading the same
input field `hooks/precompact-backup.sh` already reads. A Claude Code release
that moves the threshold then changes what a run costs, not whether it counts.

**Filler must be inert.** Four requirements, in priority order:

- *Semantically inert.* No decisions, no rejected alternatives, no promises to
  verify, no plan or phase language. Filler carrying decision structure either
  re-plants the probe answers (inflating recall) or competes with the seeded
  structure (deflating it). Inert filler keeps the seed the only decision
  structure in the window.
- *Reads, not edits.* Filler arrives as file reads. Filler edits would land in
  the "Recently edited files" section that `hooks/precompact-backup.sh` writes,
  so the unprepared condition would be scored on a snapshot half-filled with
  harness noise. This narrows the "tool calls, file edits" phrasing in Method
  above.
- *Byte-deterministic.* Filler files are generated by a harness script from a
  published seed, so a rerun on another machine produces identical bytes.
  Token counts then move only with tokenizer changes, and the run manifest
  records each file's size and SHA-256.
- *Boring to the tool surface.* Plain UTF-8 text read with the file read tool.
  No network, no command output whose length depends on the host.

**Few large reads, not many small ones.** Each turn re-sends the accumulated
prefix, so billed input over k turns tracks the running total, not the last
turn alone. Filling a window in 8 reads costs a fraction of filling it in 200,
and it removes most of the per-turn variance as well. The harness fills with
the largest chunk that completes without truncation, calibrated once per
pinned version and published as a constant.

**Order is the trap.** Filler goes strictly after the seeded structure, so the
seed is the oldest material in the window and the first candidate for
summarization. A run whose filler precedes the seed is a different and easier
experiment, and is not scored.

**Calibrate, then freeze.** Two phases:

1. *Calibration (unscored).* A doubling ladder finds the smallest filler
   budget that produces an auto receipt on the pinned version. Doubling keeps
   this cheap, and the ladder is published with the results so the constant is
   auditable rather than asserted.
2. *Scored runs.* Every auto-lane run uses that budget plus a fixed margin,
   under a hard step cap.

**Every run gets an outcome class, and all of them are reported.** `auto` (a
receipt appeared), `no-trigger` (the cap was reached first), `aborted`
(harness error or ceiling). A no-trigger run is neither retried silently nor
dropped; it appears in the results table beside the scored runs, per the
no-cherry-picking rule.

**Mid-turn compaction is a result, not a defect.** It is the case the
unprepared path exists for. The receipt records the turn index and whether the
harness was awaiting a response when the compaction landed, so between-turn
and mid-turn compactions can be counted separately instead of averaged into
one number.

**Why not script `/compact` in the auto lane?** That measures the prepared
path under the wrong label. What defines the unprepared path is that no prompt
boundary was available in which to prepare, and a scripted `/compact` hands
that boundary back.

## Metrics

| Metric | Definition |
|---|---|
| Rejected-idea re-proposal rate | probe answers that re-surface C as viable |
| Verification-skip rate | answers that green-light D without mentioning V |
| Decision recall | planted adopted/rejected pairs correctly recalled, with reasons |
| Phase accuracy | correct identification of the current plan phase |

## Conditions to compare

- Bare Claude Code (no tooling)
- cc-parachute, prepared path (`/compact-prep` before compaction)
- cc-parachute, unprepared path (mechanical snapshot only)
- compact-plus (LLM-authored state file) — measured under identical seeds

## Fairness rules

- Same seeded sessions, same probes, same scoring rubric for every condition.
- Publish everything: seeds, harness, raw outputs, scoring.
- Report the losses too. If compact-plus wins a metric, that goes in the
  README of the benchmark with the same font size as the wins.
- No cherry-picking runs: fixed N per condition, all runs reported.

## Scoring

Prefer mechanical scoring (string/semantic match against planted facts) where
possible. Where a judgment call is unavoidable, use a rubric-driven LLM judge
with the rubric published, and spot-check a sample by hand.

## Cost ceiling

**Tokens are the unit of account, not currency.** Prices and plan terms differ
per reader and change faster than the report does; a dollar figure would be
stale on publication. The report publishes billed input and output tokens per
cell next to the pinned Claude Code version and model id, and leaves the
arithmetic to the reader.

**Where the cost is.** The manual lane is cheap: seed, compact, probe. The auto
lane pays for the window twice, once to fill it and again in re-sent prefix,
which is the second reason to prefer few large filler reads. Budget on the auto
lane and the manual lane rounds to noise.

**The ceiling is a hard stop, not a target.**

- One number, declared before the first run and printed in the report header.
- One worst case per run: calibrated filler budget, plus margin, plus probes.
- The harness refuses to start a run when the ledger plus that worst case
  would cross the ceiling. It stops with the ledger intact and the report names
  the unrun cells. A truncated report is honest; a silently over-budget one is
  not.
- The ledger is append-only, one line per run, published with the raw outputs.
  It prefers a first-party usage number from the run output; where none is
  available it records a byte-derived estimate and labels that line
  `estimated`, so no reader mistakes it for a measurement.

**Starting size, and what it cannot show.** Four conditions by two lanes is
eight cells; N = 5 per cell is 40 runs, 20 of them in the expensive lane. That
N is too small to rank conditions that sit close together, and the report has
to say so in the same place it prints the numbers: at N = 5, a clean 0 of 5
still carries a 95% Wilson upper bound near 43%. Five runs catch large effects
only. Separating a 10-point difference needs an N this benchmark cannot yet
afford, and implying otherwise would repeat the failure it exists to correct.

**Raising N.** Add runs in whole batches across every cell, never to one
condition alone, and republish the earlier batch alongside the new one. Topping
up only the condition that lost is cherry-picking with extra steps.

## Harness tooling

Fail-open and jq-only govern what ships in the runtime hooks. The harness is
not in the runtime path and may use whatever tooling is convenient, provided
seeds, probes, raw outputs, and scoring are published under the fairness rules
above.

The one runtime-adjacent piece is the PreCompact receipt hook. It appends a
line to a file, writes nothing to stdout, and is installed identically in all
four conditions including bare Claude Code, so it can neither inject context
nor advantage a condition.

## Open questions

- Cross-version stability: compaction behavior changes across Claude Code
  releases; the benchmark must pin and report the version. Every calibration
  constant (filler chunk size, filler budget) is version-scoped and has to be
  re-measured after an upgrade, including when an upgrade lands mid-report.
- Content sensitivity of the summarizer: inert filler is a control, so it
  cannot tell us whether summaries degrade differently when the filler is
  itself decision-shaped. Answering that needs a second filler corpus and is
  out of scope for the first report.
- Paraphrased re-proposal: mechanical scoring catches a rejected idea restated
  in the seed's own words and misses a good paraphrase. The rubric-driven judge
  plus hand spot-check is the stated mitigation, and its agreement rate with
  the hand sample should be published rather than assumed.
